# 0019 语义检索接入位的参考实现：纯 py3 BM25

## 背景

ADR 0007 把语义检索定为「接入位」——内核（keel-lint.sh）必须零外部依赖，
检索增强由外部（Serena / embedding 服务）经 MCP 接入。但接入位长期只有
`check-mcp-config.sh` 的声明校验，**没有可运行的参考实现**：新采用方拿到
的是一个"该接什么"的空位，而不是一个"先用着、以后再换"的基线。

## 决定

新增 **可选** 参考检索器 `checks/retrieval/keel-search.py`：

- **纯 python3 标准库**（与 MCP 服务器、自测套件同一条底线），零外部依赖；
- **Okapi BM25**（k1=1.5, b=0.75），拉丁按词、CJK 按字切分；
- **接口可插拔**：`Retriever` 抽象类 + `BM25Retriever` 默认实现，换 embedding
  只需实现同一 `search(query, top_k)` 方法；
- **不进内核**：不被 keel-lint.sh 引用、不进 §9.1 检查面、不影响 lint 300s 预算；
- **自带 `--self-test`**（3 项排序断言），与 MCP 服务器同纪律。

## 为什么是 BM25 这一档（不选 embedding）

| 维度 | BM25（本档） | embedding |
|---|---|---|
| 依赖 | py3 stdlib | 模型 + 向量库（数百 MB） |
| 冷启动 | 秒级（20ms 建 48 篇索引） | 需下载模型 / 调 API |
| 可解释性 | 词频可追溯 | 黑盒 |
| 适用 | 术语 / 关键词命中为主的技术文档 | 同义改写 / 跨语言 |

Keel 的文档是**技术规范 + 坑库**，查询多为精确术语（"预算""连接池""locale"），
BM25 的词频匹配已足够；embedding 的收益（同义召回）在这个语料上不明显，
代价（依赖、冷启动、可解释性）却显著。**先把接入位跑通，再在真实查询日志证明
BM25 召回不足时升级**。

## 升级为 embedding 的条件

满足任一即启动升级（留痕到本 ADR 的 supersedes）：

1. 真实查询日志中，同义改写查询（如"上下文基座"找"龙骨定位"）BM25 top5 无命中
   且占比 > 10%；
2. 跨语言查询（英文查中文文档）成为刚需；
3. 采用方明确要求并愿意承担依赖成本。

升级方式：实现 `Retriever.search` 的 embedding 版，`keel-search.py` 加
`--backend bm25|embedding` 开关，默认仍 bm25。

## 失效场景（已知边界）

- **CJK 无分词**：按字切分，短词（如"蒸馏"）召回好，长查询精度下降；
- **不做语义同义**："上下文基座"≠"龙骨"，需靠关键词命中；
- **不索引代码**：仅热区 *.md，代码语义不在范围。

## 后果

- 好处：接入位从"空位"变"可用基线"；新采用方第一小时就能跑 `keel-search.py`
  查文档，而不是先装 Serena；接口已定，升级不破坏调用方。
- 代价：引入 py3 可选依赖（与 MCP 同族，不装不影响任何既有能力）；BM25 质量
  上限可见——但本档的目的就是"先有"，不是"最好"。
- 实测（keel 自身 49 篇，avgdl 459.6，2026-11-02）：索引构建 27.9ms；
  热路径查询中位 2.6–3.7ms、最快 2.0–2.5ms；冷启动（含建索引）23–55ms；
  QPS≈322（1000 次连续查询）。8 条术语查询中 4 条 top1 明确正确
  （预算 / 语义检索 / fork 性能 / 子模块），3 条边界命中，1 条错
  （"宪法 rule"→NOW.md，应为 CONSTITUTION.md——无分词+无同义导致）。
