# 0014 把"零 stderr 噪声"从口号变成判据（**提案，待双签**）

> **本 ADR 是提案，不是已生效的判据变更。**
> 改 `keel-lint.sh` 的判据需 owner + 双签（`CONSTITUTION.md` 人审关卡），
> 且必须同步 `DESIGN.md` §9.3 与发布仓（硬约束 1）。**本轮刻意没有动它。**

## 背景

设计稿 §9.3 声称自测套件达到「**零 stderr 噪声**」。但实测：

- `test-lint.py:406` 确实**捕获**了 stderr，`:514` 也**打印**了；
- **全脚本没有任何一处断言它为空。** 捕获 ≠ 判死。

所以 §9.3 那句话目前是**描述性的，不是可执行的**——按 §2 原则 4，
"不能被脚本判死的规则不叫规则"。

### 本轮发现的真问题

lint 每次运行 stderr 都多一行：

```
[safe-delete][SAFE_DELETE_INVALID_PATH] embedded drive prefix is not allowed
```

已查明**不是 Keel 所发**（`grep -rn "SAFE_DELETE" keel/checks/` 为空），
而是本机 PATH 上的安全删除垫片拒绝带盘符路径，导致 `keel-lint.sh:63` 的
`trap 'rm -rf "$tmp"'` 被拦（坑 `safe-delete-shim-blocks-cleanup`）。

**但这恰恰证明了缺口**：套件 38 例全 PASS，而 stderr 一直是脏的——
**噪声没有触发任何告警**。若某天 lint 真的开始吐真错误（拼错路径、编码失败），
同样不会有任何东西发现。

## 决定（待双签后执行）

**自测新增一条判据：38 例全部跑完后，若任一例的 lint 产生 stderr 噪声即判失败。**

实施要点（写清楚是为了让双签的人能预判影响）：

1. 在 `test-lint.py` 的汇总处检查每例的 `err`，非空即 fail；
2. **豁免机制必须同时做**：本机这类环境噪声会立刻让套件变红，
   而**变红的套件比没有套件更糟**（§10.4 铁律的推论）。故需要
   一个显式白名单（如 `test-lint.py` 顶部的 `STDERR_ALLOW` 列表）；
3. **豁免必须显式且可审计**——学 §9.4 的 `stale-check: off`：
   给出逃生口，但**用掉就在输出里说明**，不能静默。

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 直接把"stderr 非空即 fail"写进判据 | **会让套件在本机立刻红**。判据变更必须连豁免一起上线，否则等于把噪声变成阻塞 |
| 在 `keel-lint.sh` 里重定向 stderr 到 `/dev/null` | **那正好毁掉要测的东西**——真错误也会被吞掉 |
| 继续只打印不判定 | 就是现状。§9.3 的措辞会一直高于它的可执行性 |

## 后果

- **好处**：§9.3 的"零噪声"从形容词变成判据；lint 自身的编码/路径错误
  第一次有了被自动发现的机制。
- **代价 1**：需要维护一份环境噪声白名单。白名单本身是**负担**——
  它要求有人判断"这条噪声能不能豁免"。
- **代价 2**：判据变更触发**全套连锁**：改 `keel-lint.sh`? 否（本条只改
  `test-lint.py`），但仍须同步 `DESIGN.md` §9.3 逐字一致 + 发版 + 打 tag。
- **风险**：白名单可能被滥用成"看到噪声就加一条"。
  缓解办法：白名单条目必须写理由，且输出里显示"本次豁免了哪几条"。

## 下一步

**等双签**。在此之前不做任何代码改动——**判据放宽与判据收紧同样需要人审**。
