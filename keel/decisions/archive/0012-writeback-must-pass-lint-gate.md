# 0012 写回的上下文必须过 lint 门禁才算数

> 这条此前是**隐含**的（散在 §9.1 与 §10.4 里），本 ADR 把它提为显式原则：
> **"写回"是一次提交，不是一次写作。**

## 背景

Keel 的写回闭环（§5.5 / §10.4）要求完成任务后更新 `NOW.md`、登记坑、必要时写 ADR。
但"写回"一直有个隐含前提没被写出来：**写回的内容质量由谁担保？**

2026-10 联网核实到一条直接相关的外部证据（arXiv 2606.15828，UFMG，解剖 GitHub Top-100 仓库）：
**91% 的仓库至少含一种"配置异味"**，其中 **Lint Leakage 占 62%**——
即**把 lint 本可判死的规则抄进说明书**，用自然语言做机器该做的事。
Context Bloat 42%、Skill Leakage 35%。

**这说明"写了规则"和"规则被机器执行"在现实中是两件事**，而主流做法普遍只做了前者。
Keel 如果只在这一层用力，就会落进同一个 62%。

还有一条负面证据来自本项目自己的调研（`docs/research/context-governance-verify.md`）：
**点名失败模式，AI 就精确复现那个失败模式**——加重措辞得到的是**更精致的形式合规**。
这直接排除了"靠写得更清楚来解决"这条路。

## 决定

**任何进入热区的写回内容，必须能被 `keel-lint.sh` 判死；判不死的写法不许进热区。**

推论三条：

1. **写回走的是 pre-commit 钩子，不是"建议"**——违规内容在提交那一刻就被拦住；
2. **"写得清楚"不能替代"判得死"**——判据是 lint，不是读者的理解力；
3. **判不死的真内容要沉冷区**（§7.3「沉」），热区只留一行指针。

本 ADR 自身即是该原则的一次应用：它的取证细节全部指向
`docs/research/context-governance-verify.md` 与设计稿 §11.2，**正文不复述**（§2 原则 1）。

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 靠"写得更明确更详细"减少违规 | holaOS 取证已证伪：加重措辞反向优化，得到更精致的形式合规 |
| 让 AI 自检后再写回 | 自报不可靠（ADR 0009 已定）；且 §2 原则 4：靠自觉的不算规则 |
| 只在 CI 校验，不挂 pre-commit | 太晚——违规内容已经进了历史，而历史是**不可重建**的（ADR 0011 的回填教训） |
| 放宽判据让内容能通过 | **判据放宽等于把过去的 fail 变成沉默**（§2 原则 4 + 人审关卡：改判据需 owner + 双签） |

## 后果

- **好处**：这是 Keel 相对所有竞品**最容易被抄走形式、最难被抄走判据**的一条。
  arXiv 2606.15828 的 62% 说明赛道里缺的就是这个，而它正好长在 Keel 现有的三件套上。
- **代价 1**：会持续暴露一批"假规则"——写不进热区的东西比想象中多，
  初期 lint fail 会上升。**这是暴露存量问题，不是新增问题。**
- **代价 2**：要求每条规则都写得出一句可执行命令，这会**提高维护成本**——
  想清楚"怎么判死"通常比写清楚规则本身更难。
- **风险**：判据只覆盖"可被脚本判死"的规则；**判不死的部分（措辞、语气、示例质量）
  仍然依赖人的判断**，本 ADR 不声称解决了它。
