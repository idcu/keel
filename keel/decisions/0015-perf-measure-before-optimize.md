# 0015 性能：先查清再动手，判据失效贵于 32 秒

> 分段耗时原始数据与被否方案的实施细节见 [../checks/perf-findings.txt](../checks/perf-findings.txt)。
> 本篇只留决策与教训（§2 原则 1：每类事实只有一个定义位置）。

## 背景

日常脚本实测都<9s（load-estimate 8.5 / keel-lite 6.2 / compliance 2.5 /
verify-hooks 0.9 / MCP 0.7）。**唯一长的是 `test-lint.sh`**——41 例 × 单次 lint，约 13–15 分钟。

单次 lint 实测 **32s**（44 热区文档，Windows/Git Bash），热点集中在两段：
**段 2 frontmatter 14.5s（41%）**与**段 3 值域11.2s（31%）**，合计 72%。

根因分两类，**别混为一谈**：
- **段 2 是 fork 成本**：每文件 4 次 fork（`head -1` / `awk` / `sed|wc|tr`），
  44 文件 ≈ 176 次 × ~80ms。与 ADR 0013 的诊断同源。
- **段 3 是算法复杂度**：`fmq_set` 每次从头扫整张 FMQ 表，
  O(文件数 × 5 字段 × 表行数) = **O(n²)**，与 fork 无关。

## 决定

**采纳"自测支持子集"，放弃"抽离慢段"。**

```
bash keel/checks/test-lint.sh --only 06,39-41   # 秒级（实测 --only 39 = 3s）
bash keel/checks/test-lint.sh                    # 全量 13–15 分钟
```

支持单个 / 逗号 / 区间；用例号不存在时**报错并列出可用号**。
**纯筛选，不改任何判据**——这是它与"抽离慢检查"的根本区别。
效果：改一条判据的等待 13 分钟 → **约 3 秒**，且不牺牲任何判据强度。

> **子集通过 ≠ 可以发版。** 这句话印在输出里且必须印：子集漏掉的用例不会报。

### 放弃：批量化段 2/3（已实施、已回退）

实施中连续踩三坑，**每一个都表现为"判据静默不报"**：
① awk 下标里写 `val[pf "| status]` 字符串拼接 → `unterminated string`，
awk 退出码 1 而错误被 `2>/dev/null` 吞掉 → 段 3 一条都不报，**看上去像"通过"**；
② `flush()` 用 `FILENAME` 判文件边界 → 判定挂到错误路径；
③ 合成字段在两个分支都输出 → 表里每键两行。

**每一个都靠"造真错误验判死能力"抓出来，不是靠读代码看出来的。**
最后 `git checkout` 回退，一句话理由：

> **慢而对，胜过快而漏。判据失效的代价远大于 32 秒。**

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 段 2/3 批量化 | 实施中三次判死能力失效，风险收益比不划算 |
| lint 加 `--fast` 跳过慢段、pre-commit 用 | **本地门禁与 CI 不一致 → 可能漏判**。第 17 项刚因"判据存在却无人看"而加，不能转头又造一个"本地查得松"的缝 |
| 性能超预算从 warn 改 fail | ADR 0008 已否决：**机器慢不等于文件错**，把性能当 fail 会让人在慢机器上绕过 lint |

## 后果

- **好处**：日常改判据的迭代成本 13 分钟 → 秒级，不牺牲判据强度。
- **代价**：多一个参数，需一句"子集通过 ≠ 可发版"的提醒防误用。
- **未做**：段 2/3 真正优化（正确做法见 `perf-findings.txt`，落地时必须**独立验判死能力**）。

## 三条教训

1. **测量方法本身要先验证。** 我最初用「截断脚本法」测段耗时，
   **它漏算了段 1 之前的初始化**，于是得出"段 3/4 占 73%"的错误结论，
   并据此去优化只占 **0.04s** 的段 4——收益为零。正确做法是脚本内插桩 + 绝对时间戳。
   **错误的测量比没有测量更贵**：它让你 confidently 地优化错的地方。

2. **`2>/dev/null` 会把判据自身的崩溃一并吞掉。**
   awk 语法错误 → 退出码 1 → 输出为空 → 段 3 看起来"一条都没报"，
   而真因是**判据崩了**。这类失败最危险之处：**它长得像"通过"。**
   凡用 `2>/dev/null` 包住判据逻辑，都应单独查一次退出码。

3. **从 Python 调 bash 必须用 `shutil.which("bash")`**（坑 `harness-invokes-bare-bash`）。
   本轮所有 Python 侧测量一开始全部返回 `rc=127`，我误判为脚本问题查了好几轮——
   而这正是该坑描述的场景。**它已登记在坑库里，我仍然踩了。** 知道 ≠ 做到。

## 一条更普适的

ADR 0008 说"性能当 fail 会让人绕过 lint"，本轮反过来也验证了一次：

> **判据的性能优化与判据的正确性不是同一件事。** 前者可以慢慢做；
> 后者一旦破坏，项目就失去护栏——而**护栏失效是静默的**。
> 故取舍顺序是：**先保正确，再谈速度；速度改进优先选"不改判据"的那些。**
