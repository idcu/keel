# 0009 遵守率只测客观事实，不采信 AI 自述

> 口径与数据源的**正文在设计稿 §11.2**，本 ADR 只留"为什么这么定"与被否掉的选项。
> 实时数字用 `keel/checks/compliance.sh report` 查，不在文档里抄快照。

## 背景

§11 已有三个度量指标（返工率 / 坑复发率 / 平均阻塞时长），但它们全部度量**项目**。
没有一个数度量 **AI 本身**——它到底有没有真的遵守 Keel 的规则。
而这才是整套系统的最终目的：若 AI 拿到上下文却不照做，前三个数再好也说明不了问题。

2026-10 联网调研（逐个**读源码**，非读 README）确认三个同类项目都没有真正的遵守率，
**空白是真的**。逐条取证与源码行号见 `docs/research/context-governance-verify.md`
——**不在此复制**（§2 原则 1），本 ADR 只留决策与被否掉的选项。

## 决定

**遵守率 = 1 − (lint 命中轮次 + 放行后被回滚数) / 总检查轮次**

两个数据源都客观，**都不来自 AI 的输出**，而来自文件系统与 git 历史：

- `violations.jsonl` ← lint 的 ❌/⚠️ 命中（pre-commit 自动写）
- `load.jsonl` ← 每轮加载字节与是否超限（load-estimate.sh 自动写）
- 回滚数 ← `git log --grep=^'Revert "'`（直接读 git，不需额外文件）

**所以 AI 一个都改不了。**

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 直接问 AI"你遵守了吗"，解析它的自述 | **holaOS 的取证已证伪这条路**：门禁全部触发、AI 对 `src/client/` 零编辑、然后宣布完成；加重措辞后更糟。自报不只是不可靠，还会因过于体面而失去诊断价值 |
| 沿用 dsh-rule-lens 的口径（数拦截次数） | 它没有分母。加载 10 条违反 1 条 → 拦截 0 次 → 读起来像 100% 遵守。**数字方向是反的**，比没有数字更危险 |
| 让 AI 自报"Self-Review"（aegis 的做法） | 同第一项：把度量权交给被度量者 |
| 靠 MCP 记录 AI 读了什么来推断遵守 | 读到 ≠ 照做。加载量已经在 §7 管住了，不构成新信息 |

## 后果

- **好处**：这是本项目目前**唯一有可能做出差异化**的度量，而三件套
  （lint + pre-commit + commit-msg）**本来就全是客观的**，缺的只是聚合器。
- **代价 1**：只能测"可被脚本判死"的规则。§2 原则 4 判死不了的规则就不进分母——
  **这会反过来逼着人把规则写成可判死的**，是好事，但一开始会暴露一批"假规则"。
- **代价 2**：需要额外两个 jsonl 的存储与聚合逻辑，属于新代码面，要计入 §7 的预算审视。
- **风险**：目前**没有真实用户数据**，遵守率会长期是空序列。
  一个没有基线的指标最容易变成自欺欺人的数字——所以本 ADR 只定口径与数据源，
  **不承诺何时能给出真实数字**。回填能否造基线见 [ADR 0011](0011-backfill-is-not-compliance-rate.md)。

## v3.3.1 修正

初版只记「lint 命中」，漏了**放行后被回滚的提交**——那是 lint 自己看不见的一类不遵守。
修正后同一假仓的遵守率从 66.7% 降到 33.3%（**虚高一倍**），口径细节见设计稿 §11.2。
