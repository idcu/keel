# 第十六轮：把"发布后门面会漂"变成判据（2026-10-04）

上一轮做了全维度评估（仓根 `KEEL-全维度梳理与评估-20261004.md`），本轮按结论全量推进。
owner 已明确授权全量推进，故本轮改判据并落地。

## 本轮最重要的一件事

**把"发布后门面会漂"从一次性补正变成判据（lint 第 17 项）。**

起因是一次实测发现：发布仓 CI **当前必然 exit 1**——

```
keel-version = 3.4.4
tag v3.4.4 存在 ✅
CHANGELOG 缺 3.4.4 小节 ❌ ← CI 在这里 exit 1
```

最新小节还停在 `## 3.4.2`，3.4.3 与 3.4.4 两节都不存在。**ADR 0010 立的检查
在最近两次发布时没守住，两仓 README 徽章也停在 3.3.8。**

这与项目自己引用的外部证据同构：arXiv 2606.15828 记录 **Lint Leakage 占 62%**
（把 lint 本可判死的规则抄进说明书）。**判据存在却两周无人查看 = 没有判据。**
所以新加的检查不是"补上这一版"，而是**拦住下一次**。

## 判死能力必须独立验证

新检查不能只跑一次绿灯就信——**必须证它真会判死**：

| 场景 | 期望 | 实测 |
|---|---|---|
| CHANGELOG 缺当期小节 | 判死 | ✅ 报 `CHANGELOG.md 缺 3.4.4 小节` |
| README 徽章滞后 | 判死 | ✅ 报 `README 徽章版本 3.3.8 与 keel-version 3.4.4 不一致` |
| 纯模板安装（无 CHANGELOG/README） | **跳过不误判** | ✅ 无版本相关报错 |

第三条最容易漏：**"副本不存在"不能被当成"副本不一致"**，否则所有从
`git clone` 装的用户第一屏就是红的。

## 顺带修掉的两个真实缺口

**其一：`%TEMP%` 泄漏。** 坑文档原写"不要为此改 Keel"——对判据成立，
对泄漏不成立（历史堆积 301 个目录）。根因是 `mktemp -d` 在 Windows 返回
`C:\Users\…\Temp/tmp.X`（**含盘符且混用两种分隔符**），删除垫片按规则拒绝。
改法是**归一化路径**（`pwd -P`），不是往判据里加过滤器。
实测：stderr 首次完全干净。

**其二：新文件静默漏发。** `install.sh` 的就地升级是**显式文件白名单**，
而 `keel-doctor.sh` 不在其中——老用户升级拿不到，**且没有任何检查会报**
（工具链缺失不在判据覆盖内）。这属于典型的静默失效，已补进白名单
（并让它总是覆盖：纯诊断脚本没有"用户改过"这种语义）。

## 四个踩坑记录（下轮别再犯）

1. **共享脚本可同步，文档必须各改各的。** 我曾把项目仓的 `decisions/INDEX.md`
   直接拷到发布仓，但两仓 ADR 集合不同（项目仓有 0013/0014）→ 发布仓立刻出
   3 条死链。**这是"两仓内容独立演进"原则的具体体现。**
2. **判死能力 ≠ 自身正确性。** 修路径归一化时初版写 `tmp_posix=$(…) || tmp_posix=""`，
   在 `set -u` 下偶发把路径置空，下游报 `sed: can't read :`，**3 个用例连带失败**。
   它长得像"环境问题"，实际是判据自身失效。**判死能力（能抓真错误）通过了，
   不代表自身正确性（不因环境假设而崩）成立。**
3. **新文件会静默漏发**（见上）。
4. **评估报告的判断也会被实测推翻。** 评估里写"蒸馏坑应移出热区"，
   实测被 §5.4 否掉：`distilled` 的规格语义就是"已上提宪法（**细节留存**）"，
   而"移入 archive/"是 `archived` 的语义；§7.4 流程也明写"真踩了才点开全文"。
   **搬走仍需全文的坑，会让 CONSTITUTION 与 pitfalls/INDEX 的引用变成死链。**
