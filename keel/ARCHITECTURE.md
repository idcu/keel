# ARCHITECTURE

> **只画现状，不写愿望**：这里写"现在是什么样"，不是"希望变成什么样"——愿望写在
> `CONSTITUTION.md` 的身份段。改了模块边界或依赖方向，等于改了红线，走人审关卡。
> 规格见《Keel 设计稿》§5.3。

## 仓库拓扑（两个仓，各有唯一真源）

| 仓 | 路径 | 唯一真源 | 可见性 | 说明 |
|---|---|---|---|---|
| 规格仓 | 本仓（`keel`） | `DESIGN.md` | 公开 | 规格在这里版本化；不含发布仓源码历史 |
| 发布仓 | `keel-starter/`（子模块） | `keel/` 模板 | 公开可分发 | 纯模板，**不含设计稿** |

依赖方向是**单向**的：

```
规格仓 (keel)  ──子模块指针──>  发布仓 (keel-starter)
     │                              │
     │ 规格（DESIGN.md）             │ 模板（keel/）
     └──────── 派生 ────────────────┘
```

**发布仓不知道规格仓存在**（它不含 `DESIGN.md`）；
**规格仓知道发布仓的每个文件该长什么样**（`test-lint.sh` 的 DOC 检查逐字比对）。
这个不对称是有意的：模板要能被不认识 Keel 规格的人直接用。

## `keel/` 目录的两个身份（本仓最容易混淆的一点）

同一份 `keel/` 结构，在两个仓里语义不同：

| 位置 | 身份 | 谁改它 | 变更方式 |
|---|---|---|---|
| `keel-starter/keel/` | **模板**（给用户项目的骨架） | 发布仓维护者 | 改发布仓 → 提交 → 更新本仓子模块指针 |
| `keel/`（本仓根） | **实例**（Keel 项目自己的上下文基座） | 本仓任何会话 | 直接改；升级时按字段增量合并，不整体覆盖 |

**为什么实例要复制而不是软链子模块**：子模块是"别人的模板"，NOW.md 记的是别人的进度。
实例必须能记本项目自己的坑、自己的 ADR、自己的当前焦点。
两者结构相同是**刻意的**（实例照模板长），但内容各自独立演进。

## 关键数据流

1. `规格改动 → 同步 DESIGN.md §9.3 代码块 → 发布仓 keel-lint.sh → 更新子模块指针 → 项目仓 CI 复验`
2. `会话开始 → 读 keel/INDEX.md + keel/NOW.md → 按检索协议定位 → 完成任务写回 NOW.md`
3. `commit message 写 "pitfall: <文件名>" → commit-msg 钩子 → 该坑 triggers +1 → 达阈值告警蒸馏`

## 契约

契约（API / 类型 / 事件）的**唯一真源是 `keel/contracts/`**。
本文件只描述边界与方向，不复制任何字段定义——能引用的绝不复制，否则必然漂移（§2 原则 1）。

> Keel 自身目前**没有对外 API**，故 `contracts/` 只有索引与 schema 模板。
> 一旦对外提供 MCP 资源或 CLI 参数契约，真源立刻落到这里，不写在别处。
